# Interrupts and Power

## Definition

§3.18 specifies the SMMU interrupt model — how the SMMU signals software about events, CMD_SYNC completion, and errors, using either Message Signaled Interrupts (MSI) or wired interrupts. §3.19 describes power control: automatic power saving, software-requested power-off, and the Dormant state.

---

## §3.18 Interrupt Sources and Delivery

### MSI vs. Wired Interrupts

The SMMU must support **wired interrupts**, **MSI**, or both. Discovery:
- **SMMU_IDR0.MSI==1:** MSI is supported.
- Wired interrupt support is IMPLEMENTATION DEFINED; discovered via an IMPL DEFINED mechanism (not an architectural register field).

**Arm recommendation:** Do not support Secure MSIs without also supporting Non-secure MSIs.

### MSI Format

An MSI is a 32-bit data write to a configurable address:
- Non-secure MSIs are typically directed to `GICD_SETSPI_NSR` or `GITS_TRANSLATER`.
- Secure MSIs use `GICD_SETSPI_SR`.
- The MSI target address and data are configured in the per-source `*_IRQ_CFG0`/`*_IRQ_CFG1`/`*_IRQ_CFG2` registers.
- **Memory type and Shareability** for MSI writes are configurable (via IRQ_CFG2 fields).

### DeviceID for MSI

When the SMMU sends MSIs to an ITS:
- The SMMU uses its own unique DeviceID that is **distinct from all client device DeviceIDs** routed through it. The SMMU does not pass client StreamIDs as its own DeviceID.
- Client device StreamIDs are passed as EventIDs or through separate routing.

### Ordering Rule

An interrupt is **not observable** by software until the information that triggered it is also observable. That is, if the SMMU writes an event to the event queue and then signals an interrupt, software that observes the interrupt must also be able to observe the event queue entry. This prevents a race where the interrupt handler reads the queue before the entry is visible.

### Coalescence

MSIs may be coalesced — a single MSI delivery may represent multiple triggering events. However, coalescence must **not significantly delay** interrupt delivery. The architectural intent is that software polling the queue after an interrupt will find all entries that triggered that interrupt.

## §3.18.1 MSI Synchronization Points

Two architectural fence operations are defined for MSI synchronization:

**Fence 1 — Disable via IRQ_CTRL:**
Disabling an MSI source via `IRQ_CTRL` provides a synchronization point: after the IRQ_CTRL write takes effect (acknowledged by IRQ_CTRLACK), all prior MSIs from that source have completed. "Completed" means: the MSI write is either **visible** in the GIC (interrupt pending) **or** the abort is visible in `GERROR` with the `MSI_*_ABT_ERR` bit set.

**Fence 2 — CMD_SYNC completion:**
When a CMD_SYNC completes (SMMU writes the completion event or MSI), all MSIs generated by commands prior to that CMD_SYNC on the **same queue** have also completed per the definition above. This allows software to drain MSI delivery by issuing CMD_SYNC and waiting for its completion.

**Re-enable procedure:** When re-enabling an MSI source after having disabled it, the SMMU uses the new configuration registers. Any MSI arising after re-enable uses the newly configured address/data.

## §3.18.2 Interrupt Sources

The SMMU defines 13 architectural interrupt sources. Each is enabled independently via `SMMU_IRQ_CTRL` (and the corresponding Secure/Realm/Root variants):

| Source | Trigger Condition | Register |
|--------|-------------------|----------|
| Event queue (NS) | Queue transitions from empty to non-empty | SMMU_EVENTQ_IRQ_CFG* |
| Event queue (Secure) | Secure queue empty→non-empty | SMMU_S_EVENTQ_IRQ_CFG* |
| PRI queue (NS) | `PRIQ_IRQ_CFG2` overflow condition or non-empty | SMMU_PRIQ_IRQ_CFG* |
| CMD_SYNC completion (NS) | NS command queue CMD_SYNC completed | SMMU_CMDQ_IRQ_CFG* |
| CMD_SYNC completion (Secure) | Secure queue CMD_SYNC completed | SMMU_S_CMDQ_IRQ_CFG* |
| GERROR (NS) | A new error condition becomes active in SMMU_GERROR | SMMU_GERROR_IRQ_CFG* |
| GERROR (Secure) | A new error in SMMU_S_GERROR | SMMU_S_GERROR_IRQ_CFG* |
| Realm Event queue | Realm queue empty→non-empty | SMMU_R_EVENTQ_IRQ_CFG* |
| Realm PRI queue | `SMMU_R_PRIQ_IRQ_CFG2.LO` condition | SMMU_R_PRIQ_IRQ_CFG* |
| Realm CMD_SYNC | Realm command queue CMD_SYNC completed | SMMU_R_CMDQ_IRQ_CFG* |
| Realm GERROR | A new error in SMMU_R_GERROR | SMMU_R_GERROR_IRQ_CFG* |
| GPF_FAR | An error is active in SMMU_ROOT_GPF_FAR | (Root page) |
| GPT_CFG_FAR | A GPT configuration error is active | (Root page) |

All 13 sources are **transient / edge-triggered** — the interrupt fires on the transition to the condition, not level-triggered on the sustained condition. For the queue sources, this means the interrupt fires once when the queue first becomes non-empty; software must drain the queue and re-arm.

**RME additional wired interrupts (§3.25.5):** RME implementations add two additional wired interrupts for Root/Realm security state error signaling. These are not MSI-capable in all implementations.

## §3.19 Power Control

### Automatic Power Saving

An SMMU may implement IMPLEMENTATION SPECIFIC automatic power saving (e.g., clock gating, power gating internal structures). This is functionally invisible to software:
- The SMMU **may or may not** retain cached structures/translations across a power-saving state.
- The SMMU **must not** corrupt any architectural state as a result of power saving.
- The SMMU **must** wake on demand — any incoming client transaction or software access to SMMU registers must cause the SMMU to wake and function correctly.

Automatic power saving requires no software involvement and is transparent.

### Software-Requested Power-Off

Software may request a full SMMU power-off via an IMPLEMENTATION DEFINED mechanism. The following preconditions must all be satisfied before power-off:

1. All Security states (Non-secure, Secure, Realm, Root as applicable) must have agreed to power-off. No unilateral power-off by one Security state.
2. All client DMA must be **disabled** — no client device may issue new transactions.
3. All **in-flight transactions** from all clients must have **completed** (responses returned).
4. All **stalled transactions** must be **terminated with abort** before powerdown. Stalled transactions cannot be left pending across a power-off; the SMMU must not attempt to resume them after power-on.

After these conditions are met, the SMMU may be powered off. After power-on:
- A **full reset and re-initialization** is required before the SMMU can process transactions. The power-off state is equivalent to a cold reset.
- No caches, TLBs, or configuration are retained across a power-off.

## §3.19.1 Dormant State

The Dormant state is an optional low-power state in which the SMMU guarantees specific properties about its cached state. It is separate from automatic power saving and power-off.

**SMMU_STATUSR.DORMANT==1 guarantees:**
- No cached structures (STEs, CDs, etc.) from system memory are retained.
- No cached translations (TLB entries) from translation table walks are retained.
- The SMMU **will** re-fetch all structures and translations from memory when next needed.
- No speculative prefetch of structures or translations is in progress.
- No stale data from previously cached structures will be used.

### Software Use of Dormant

The Dormant flag provides an optimization for software that needs to update structures without issuing explicit invalidation commands:

1. Software updates a structure in memory (e.g., modifies an STE or CD).
2. Software issues a DSB to ensure the write is globally visible.
3. Software reads `SMMU_STATUSR.DORMANT`.
4. **If DORMANT==1:** No cached copies of any structure are present. Software can **skip** issuing CMD_CFGI_*/CMD_TLBI_* for the modified structures, because the SMMU will re-fetch from the updated memory on next use.
5. **If DORMANT==0:** The SMMU may have cached copies. Software must issue the appropriate invalidation commands and CMD_SYNC before relying on the new structure content.

Both the Dormant implementation (by the SMMU) and the Dormant optimization (by software) are **optional**. Software that does not use Dormant must always issue invalidation commands; the Dormant shortcut is only valid when DORMANT==1.
