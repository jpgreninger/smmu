# SMMU Queue Mechanics

A complete reference for implementing SMMU circular buffer queues in a functional or performance model. Covers Command queue, Event queue, PRI queue, and Enhanced Command queues (ECMDQ).

## Queue Architecture Overview

The SMMU has three queue types per security state:

| Queue | Direction | Producer | Consumer | Security states |
|-------|-----------|----------|----------|----------------|
| Command queue | Input (SW→SMMU) | Software | SMMU | NS, Secure, Realm |
| Event queue | Output (SMMU→SW) | SMMU | Software | NS, Secure, Realm |
| PRI queue | Output (SMMU→SW) | SMMU | Software | NS, Realm (optional) |

Optional: Enhanced Command queue (ECMDQ) — up to 256×256 additional command queues per security state.

## Mirrored Circular Buffer Implementation

All queues use the same mirrored circular buffer scheme. Key properties:
- Size: `2^n` entries, `0 ≤ n ≤ 19`. Configured at initialization.
- Index registers: `PROD` (producer write index) and `CONS` (consumer read index). Each is a 20-bit register.
- Actual index is bits `[n-1:0]`; wrap bit is bit `[n]`; bits `[19:n+1]` are ignored.

### Index Register Layout (for queue size 2^n)

```
Bit [19]...[n+1] [n]        [n-1]...[0]
     Ignored      Wrap bit   Index (n bits)
```

### State Detection

| Condition | State |
|-----------|-------|
| `PROD.WR[n:0] == CONS.RD[n:0]` (including wrap) | Empty |
| `PROD.WR[n-1:0] == CONS.RD[n-1:0]` AND `PROD.WR[n] != CONS.RD[n]` | Full |
| Otherwise | Partially full (can produce OR consume) |

### Index Advancement Rules

1. Both producer and consumer may only **increment** the index (by 1 per entry).
2. When incrementing past entry `2^n - 1`, the index wraps to 0 **and** the wrap bit toggles.
3. The wrap bit toggle and index reset must be performed atomically (as a single register write).
4. Neither producer nor consumer may decrement or arbitrarily set the index.

### Consistency Invariant

Valid states:
- `PROD.WR == CONS.RD` and `PROD.WR_WRAP == CONS.RD_WRAP` → empty
- `PROD.WR == CONS.RD` and `PROD.WR_WRAP != CONS.RD_WRAP` → full
- `PROD.WR > CONS.RD` and `PROD.WR_WRAP == CONS.RD_WRAP` → partially full
- `PROD.WR < CONS.RD` and `PROD.WR_WRAP != CONS.RD_WRAP` → partially full

Invalid (CONSTRAINED UNPREDICTABLE — must not be written):
- `PROD.WR > CONS.RD` and `PROD.WR_WRAP != CONS.RD_WRAP`
- `PROD.WR < CONS.RD` and `PROD.WR_WRAP == CONS.RD_WRAP`

Model behavior on inconsistent state: pick one of the permitted CONSTRAINED UNPREDICTABLE behaviors (consume at UNKNOWN location, stop consuming, or treat as full) and document the choice.

## Command Queue Specifics

- **Software** writes entries to `SMMU_CMDQ_BASE + PROD.WR × entry_size`, then increments `SMMU_CMDQ_PROD`.
- **SMMU** reads from `SMMU_CMDQ_BASE + CONS.RD × entry_size`, processes the command, then increments `SMMU_CMDQ_CONS`.
- Commands are consumed in-order within a queue.
- Memory attributes for queue access: `SMMU_CR1.{QUEUE_SH, QUEUE_OC, QUEUE_IC}`.

### Queue Enable/Disable Handshake

Enable: `SMMU_CR0.CMDQEN = 1` → wait for `SMMU_CR0ACK.CMDQEN = 1`.
Disable: `SMMU_CR0.CMDQEN = 0` → wait for `SMMU_CR0ACK.CMDQEN = 0`. At this point, command consumption has stopped and error state is stable.

### Command Error Handling

If a command error occurs (unknown opcode, illegal parameters):
- `SMMU_CMDQ_CONS.ERR` is set with the error reason.
- Queue processing **stops** at the error point.
- Software must clear the error (write to `SMMU_CMDQ_CONS.ERR`) to resume.
- A halted command queue is a global error condition; see `SMMU_GERROR.CMDQ_ERR`.

### CMD_SYNC Completion Signals

`CMD_SYNC` parameters:
- `ComplSignal == 0b00`: no signal (poll `SMMU_CMDQ_CONS` for completion).
- `ComplSignal == 0b01`: MSI write to `MSIAddress` with `MSIData` when complete.
- MSI write uses `MSIWriteAttributes` for memory type/shareability.

CMD_SYNC semantics: when consumed, ALL effects of commands previously consumed on the SAME queue are complete. This includes memory-visible event queue updates for any faults generated by those commands.

## Event Queue Specifics

- **SMMU** writes entries to `SMMU_EVENTQ_BASE + PROD.WR × entry_size`, then increments `SMMU_EVENTQ_PROD`.
- **Software** reads from `SMMU_EVENTQ_BASE + CONS.RD × entry_size`, then increments `SMMU_EVENTQ_CONS`.
- Multiple event sources compete for the Event queue (all streams, all translation stages).

### Visibility Guarantee

The SMMU updates `PROD.WR` no earlier than when all written event data is observable in the Shareability domain. Software must not read a queue entry beyond the last observed `PROD.WR` (data at that location is UNKNOWN).

### Overflow Behavior

- Non-stall events: may be silently dropped if queue is full.
- Stall events: never dropped. Buffered internally until queue has space.
- Overflow indicator is set in `SMMU_GERROR.EVENTQ_ABT` when an Event queue external abort occurs.

### Interrupt Assertion

- The SMMU asserts the Event queue interrupt no later than when `PROD.WR` is updated.
- Interrupt handler must read `PROD.WR` before assuming new events are present.
- A single interrupt may cover multiple event records.

## PRI Queue Specifics

- Present when `SMMU_IDR0.PRI == 1` and `SMMU_CR0.PRIQEN == 1`.
- Receives PCIe Page Request messages from endpoints.
- Same circular buffer mechanics as Event queue (SMMU is producer).
- Software processes requests, resolves page mappings, then issues `CMD_PRI_RESP` to the Command queue.
- If translation is disabled (`SMMUEN == 0`): all Page Requests are denied as if `PRIQEN == 0`.

## Enhanced Command Queue (ECMDQ)

### Discovery

- `SMMU_IDR1.ECMDQ == 1` indicates ECMDQ support.
- Number of control pages: `2^SMMU_IDR6.CMDQ_CONTROL_PAGE_LOG2NUMP`.
- Each control page registers: `SMMU_CMDQ_CONTROL_PAGE_BASE<n>`, `SMMU_CMDQ_CONTROL_PAGE_CFG<n>`, `SMMU_CMDQ_CONTROL_PAGE_STATUS<n>`.

### ECMDQ Register Layout (within control page)

Each ECMDQ occupies 16 bytes:

| Offset | Register | Size |
|--------|----------|------|
| 0x00   | `SMMU_ECMDQ_BASE<n>` | 64-bit |
| 0x08   | `SMMU_ECMDQ_PROD<n>` | 32-bit |
| 0x0C   | `SMMU_ECMDQ_CONS<n>` | 32-bit |

### ECMDQ Enable/Disable

Enable: `SMMU_ECMDQ_PROD<n>.EN = 1` → wait for `SMMU_ECMDQ_CONS<n>.ENACK = 1`.
Disable: `SMMU_ECMDQ_PROD<n>.EN = 0` → wait for `SMMU_ECMDQ_CONS<n>.ENACK = 0`.

On reaching disabled state: errors reported, consumption stopped, `CONS.{ERR_REASON, ERR, RD_WRAP, RD}` are stable.

### ECMDQ Scheduling

- The SMMU may consume from multiple ECMDQ queues in parallel.
- No guaranteed total order between commands on different queues.
- Round-robin or weighted round-robin scheduling is IMPLEMENTATION DEFINED.
- `CMD_SYNC` on an ECMDQ synchronizes only commands on that specific ECMDQ.
- `CMD_SYNC` on the main `SMMU_(*_)CMDQ` does NOT synchronize ECMDQ commands.

### ECMDQ Error Protocol (§3.5.6.3)

ECMDQ errors use a **toggle protocol**, not a set/clear protocol:

1. On encountering a fetch or processing error, the SMMU:
   - **Toggles** `SMMU_ECMDQ_CONS<n>.ERR` (0→1 or 1→0).
   - Writes the error reason to `SMMU_ECMDQ_CONS<n>.ERR_REASON`.
   - Sets `SMMU_ECMDQ_CONS<n>.RD` and `RD_WRAP` to point at the failing command.
2. While `SMMU_ECMDQ_PROD<n>.ERRACK != SMMU_ECMDQ_CONS<n>.ERR`, the SMMU **stops consuming** from that queue.
3. **Recovery procedure:**
   a. Disable the ECMDQ (`EN=0`, wait for `ENACK=0`).
   b. Read and record `ERR_REASON`, `RD`, `RD_WRAP`.
   c. Write `ERRACK` to match the current `ERR` value.
   d. Optionally re-position `PROD` past the offending command.
   e. Re-enable the ECMDQ.

ECMDQ errors are additionally reported in `SMMU_GERROR.CMDQP_ERR` (Non-secure) or `SMMU_S_GERROR.CMDQP_ERR` (Secure) — independent of the main `SMMU_GERROR.CMDQ_ERR`. The ordering guarantee: `CMDQP_ERR` becoming observable implies the corresponding `SMMU_ECMDQ_CONS<n>.ERR` is already observable.

If a `CMD_SYNC` MSI write (via a Command queue control page) experiences an External abort → reported in `SMMU_(*_)GERROR.MSI_CMDQ_ABT_ERR`.

### ECMDQ Non-full WFE

If `SMMU_IDR0.SEV == 1`: SMMU sends WFE wake-up event when any ECMDQ transitions from full to non-full.

### CR1 Interaction

If any ECMDQ is enabled: `SMMU_(*_)CR1.{QUEUE_SH, QUEUE_OC, QUEUE_IC}` become read-only (locked to current value, since ECMDQ uses them too).

## Queue Memory Access Attributes

Queue accesses (for both SMMU-originated and software-originated) use:
- Shareability: `SMMU_CR1.QUEUE_SH`
- Outer cacheability: `SMMU_CR1.QUEUE_OC`
- Inner cacheability: `SMMU_CR1.QUEUE_IC`

These must be configured before enabling queues.
